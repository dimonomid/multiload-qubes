# Multiload for Qubes

A native GTK3 XFCE panel plugin with scrolling host/per-qube CPU, host/per-qube RAM, network, swap and disk I/O graphs.
All charts are one panel item: move them together using XFCE's normal menu.
Rust implements collection, snapshot validation, history, Cairo rendering, GTK3
preferences, panel settings and custom theme storage. A small C adapter only
registers the XFCE plugin and bridges its panel API. The collector CLI uses clap;
Cargo.lock pins dependency versions. Slint is not required.

## Graphs

- **CPU:** blue (`#036F96`), the change in Xen domain CPU time divided by elapsed
  wall time and host logical CPU count. 100% means all logical CPUs are busy.
  Includes dom0 and raw supporting domains once; this is scheduled domain CPU
  time, not a measurement of all hypervisor execution overhead.
- **Qube CPU:** immediately after host CPU, bright blue lines show CPU time
  divided by elapsed time and each domain's online vCPU count. The fixed scale is
  0–100% per domain, with a dark-blue maximum fill and pixel-sharp lines, including
  dom0. The tooltip lists the busiest qubes, online vCPU counts and their host-wide
  CPU contributions. Scheduling contention can keep a busy qube below 100%; this
  measures scheduled CPU time rather than time waiting for Xen to schedule it.
- **RAM used:** green (`#03964F`), `MemTotal − MemAvailable` sampled inside guests
  and dom0. This estimates RAM in use after accounting for reclaimable cache and
  excludes swap.
- **RAM allocated spare:** lighter green (`#43D18D`), current Xen allocation with known usage minus
  known used RAM. This includes cache and buffers as well as free memory inside guests.
  This is current allocation, never configured `maxmem`.
- **Unknown usage:** red (`#D14343`, multiload-ng’s load color) portion within allocation when a guest does not provide
  the required reports. Used is then a lower bound, identified in the tooltip.
- RAM is scaled against Xen's physical total. The tooltip separately lists Xen
  and unattributed overhead. That overhead is not painted as guest-used RAM.
- **Qube RAM:** directly after host RAM, bright green lines show each reporting
  domain's `(MemTotal - MemAvailable) / MemTotal` on a fixed 0–100% scale, including
  dom0. A subtle dark-green fill follows the highest percentage; lines
  overlap rather than stack. Its tooltip lists the highest percentages, used/total
  RAM and reporting coverage. Missing reports and restarted qubes break lines.
  The denominator is current guest-visible RAM, so ballooning can change the
  percentage without an application allocating more memory.
- **Network:** incoming yellow (`#E2CC05`), outgoing olive (`#696018`), stacked
  rates from sys-net’s physical NICs. The scale follows the visible combined peak
  (rounded up to a power of two, with a 1 KiB/s minimum). Tooltips show KiB/s or
  MiB/s. This measures traffic on external interfaces, including protocol overhead
  and traffic generated by sys-net, rather than application payload alone.
- **Swap:** thin purple lines per reporting domain on a fixed 0–100% scale;
  100% means that domain's enabled swap is full. A translucent fill under the
  highest percentage shows the peak across reporting domains at each instant.
  Percentages overlap rather than stack. Lines use deterministic tints of
  multiload-ng's swap purple (`#9C43D1`), with its border (`#510080`) and gradient.
  The tooltip lists known used/enabled totals, reporting coverage including dom0,
  and the five highest users by individual percentage. Disabled swap has no line;
  missing reports leave gaps and grey baseline marks, rather than fake zeroes.
  Restarted qubes start new line segments; historical lines remain until they scroll out.
- **Disk I/O:** orange reads (`#ED7A00`) and light-orange writes (`#FFAB73`),
  stacked bytes/second across supported physical disks visible in dom0. The
  automatic scale follows the visible combined peak, rounded to a power of two
  with a 1 KiB/s minimum. Its tooltip lists read/write rates and monitored disks.
  This measures physical-device traffic, including guest storage and dom0 I/O,
  rather than filesystem space occupied or disk busy percentage.
- Stale/missing snapshots produce gaps with grey baseline marks, not fake zeroes.

Colors, borders and dark gradient backgrounds match multiload-ng's default
palette: <https://github.com/udda/multiload-ng/blob/master/common/colors.c>.
The implementation is new; LICENSE contains GPL-2.0, with this project licensed
under GPL-2.0-or-later.

## Build on the development machine

```bash
sudo dnf install rust cargo gcc make pkgconf-pkg-config gtk3-devel xfce4-panel-devel xen-devel
cargo fetch --locked
make
make test
```

GTK3 bindings are enabled by the optional Cargo `panel` feature. A standalone
collector build does not enable it:

```bash
cargo build --release --offline --no-default-features --bin multiload-qubes-collector
```

`make` builds the collector first, then the panel library with `--features panel`,
and keeps a separate panel archive in `build/` for the C adapter to link. This
prevents standalone Cargo builds from replacing the panel archive with a library
that has GTK disabled. The UI modules live in `src/panel/`: preferences, config,
theme files, runtime and preview/integration checks. Only `native/plugin.c` uses
the XFCE C API.

Optional lint tools: `sudo dnf install rustfmt clippy`, then `make check`.
Optional GUI tests: `sudo dnf install xorg-x11-server-Xvfb`, then `make gui-test`.
These test the shared plugin entry point and widget lifecycle, as well as settings
and persistence, using an isolated virtual display and temporary configuration.
Rust/Cargo and the development dependencies have already been installed on this
development machine. The plugin is not installed in your panel automatically.

Run `build/multiload-qubes-preview` for a clearly labelled **simulated** preview.
Add `--preferences` to inspect the Rust preferences dialog.
It does not require Xen or alter the panel. For an image without a display:

```bash
build/multiload-qubes-preview --render build/preview.png
```

## Build an RPM for dom0

```bash
sudo dnf install rpm-build systemd-rpm-macros
make rpm
```

To put temporary RPM build files on a separate filesystem:

```bash
make rpm
```

RPMs and a source RPM are written under `build/rpm/`. The source RPM bundles
Cargo dependencies and builds offline; the initial development checkout needs
`cargo fetch --locked` once before the offline Make targets. **Build against your dom0
distribution**, typically in a matching disposable build VM. An RPM compiled on
this Fedora 43 development machine is not guaranteed to run on an older dom0:
Rust, GLib, GTK and glibc minimum versions can differ. Use the source RPM or source
tree in the matching build environment. No Rust compiler is needed at runtime.

Transfer the resulting matching RPM into dom0 through your normal Qubes file
transfer procedure. In dom0:

```bash
sudo dnf install ./multiload-qubes-0.11.1-1*.rpm
sudo systemctl enable --now multiload-qubes-collector.service
```

Add **Multiload for Qubes** through **Panel Preferences → Items → Add**. It is a
native panel item, not a notification-area icon. Right-click → Properties changes
chart width (0 = square), refresh interval, and visible charts. Settings persist
per panel instance. Hovering a chart shows only its own metrics; moving between
charts switches the tooltip. Network and disk tooltips also state the speed
represented by a full chart, using the combined in/out or read/write scale for
the currently visible history. Resizing a chart updates that scale. Vertical
panels stack the graphs and use the same per-chart tooltips. Properties labels
the individual-domain charts `Per-qube CPU`, `Per-qube RAM` and `Per-qube swap`.
At least one chart stays enabled.

Appearance is configured in its own Properties tab: choose Original, Tango,
Solarized Dark, Solarized Light or Solarized Light Gradient, then customize each
chart. Solarized Light has a flat opaque background; its Gradient variant fades
from warm cream to transparency. All colors include
opacity: background top/bottom, border, series, per-qube base lines and maximum
fill, and missing-data marks. A transparent-background checkbox clears both
background opacities. Border color and width are together; 0 px removes it. All presets use 0 px borders.
Per-qube lines retain stable derived shades (darker against light backgrounds).
The checkerboard preview uses simulated data; changes also preview on the panel.
Editing a built-in or saved theme switches to **Custom draft**, keeping the
source theme intact. **Save as…** creates a named custom theme; selecting an
existing name asks before overwriting it. **Save changes** updates the source
custom theme, also with confirmation. Built-ins and their names are protected.
Saved custom themes can be renamed or deleted. Switching themes or resetting
appearance while a draft is unsaved asks whether to discard it.

**Apply** saves the panel appearance (including an unsaved draft and its source);
**Cancel** restores the appearance from when Properties opened. Applying a draft
does not save a named theme. Explicit theme saves, renames and deletes take
effect immediately and are independent of Apply/Cancel. Deleting a theme keeps
its current colors as a draft. Reset restores the original appearance settings.

Each custom theme is stored in a separate GLib key file under
`$XDG_CONFIG_HOME/multiload-qubes/themes/` (normally
`~/.config/multiload-qubes/themes/` in dom0). Files use generated UUID filenames
with a `.theme` extension, so display names may contain spaces, Unicode or `/`.
The `[Theme]` section contains `Version=1` and `Name`. Each chart has a section
(`CPU`, `RAM`, `Network`, `Swap`, `Disk`, `PerQubeRAM`, `PerQubeCPU`) containing
`Border`, `BackgroundTop`, `BackgroundBottom`, `Series1`, `Series2`, `Series3`,
`Missing` as `#RRGGBBAA`, and `BorderWidth` as an integer from 0 to 16.
Theme writes use atomic replacement; invalid/incomplete files, unknown versions
and duplicate names are skipped with a notice in Properties. Theme lists reload
when Properties opens. Theme files are shared by panel instances for the same
user. Import/export buttons are not included; copying a valid `.theme` file into
this directory makes it available next time Properties opens.


To remove it, first remove the panel item, then:

```bash
sudo systemctl disable --now multiload-qubes-collector.service
sudo dnf remove multiload-qubes
```

For a staged install without touching the system: `make install DESTDIR=/tmp/mq-stage`.

## Collector and memory semantics

The dom0 collector is a compiled **Rust executable**. It reads native Xen
statistics through libxenstat and domain identities through libxenstore. Opaque
handles avoid copying Xen-version-specific C structures into Rust. The installed
libxenstat is loaded from system library directories using `libloading`. Version
symlinks are deduplicated, each candidate must expose the complete required API,
and an unloadable/incomplete candidate is skipped in favor of the next one.
Failures include candidate paths, loader details and missing symbol names. The
private function table owns the library until native cleanup completes. C signatures
remain an audited FFI contract; symbol presence cannot prove ABI compatibility.
The binary is not linked to the build machine’s versioned libxenstat soname. Runtime Xen libraries come from `xen-libs`; building needs
`xen-devel` for the XenStore linker library. Live access still needs testing in dom0.

Only the collector service has Xen privileges; the GUI never runs as root. Rust
handles CPU accounting, guest connection lifecycle, memory aggregation, validation,
timeouts and atomic publication at `/run/multiload-qubes/metrics`. Unix descriptor flags and process-group signals use `nix`; scoped SIGINT/SIGTERM
registrations use `signal-hook`. The systemd unit and collection options remain
unchanged; MQ6 extends snapshots with per-domain CPU budgets and scheduled time. Sampling defaults to 1s; changing the
panel refresh interval changes chart history sampling, not collection frequency.

The remaining Python code is the small payloads in `guest/memory.py`
and `guest/network.py`, embedded in the Rust binary and sent through Qubes' existing
`qvm-run` tool. Nothing is installed inside guests. Qubes' own `qvm-run` is itself
Python software; this refactor removes our Python collector, not Qubes' Python
runtime. No balloon targets, XenStore keys/permissions, or qmemman behavior change.

For dom0 and each reporting Linux guest:

```text
used RAM = MemTotal - MemAvailable
```

`MemAvailable` accounts for memory the kernel estimates it can make available
without swapping, including reclaimable cache. Used RAM is not a sum of process
RSS, and swap usage is not added. This is the same calculation inside guests and
dom0. This replaces the pre-0.3 XenStore `meminfo`/`swapinfo` calculation entirely:
missing `swapinfo` and disabled Qubes memory balancing no longer prevent reporting.
Usage can differ from older chart versions because the definition is now based
on available memory instead of subtracting all buffers/cache.

A persistent connection per running qube reads `/proc/meminfo` once per second.
The guest must have the normal Qubes command agent, Python 3 and `xenstore-read`.
Names come from dom0's XenStore domain names and are validated before use. Each
report includes its guest domid; the collector also tracks XenStore VM UUID paths and
starts fresh connections when domain identities change. It never starts or
unpauses qubes. Paused, stopped, unsupported or unreachable guests, internal
stubdomains and guests missing required tools do not contribute a guessed usage.
Their current allocation stays red. Readings expire after five seconds without
a valid report; failure in one guest does not block CPU, network or other guests.

During ballooning, used values are clamped to current Xen allocation because
allocation and guest readings are not simultaneous. Light green is the remaining
allocation of reporting guests; red is the full allocation of non-reporting guests.
Xen/unattributed overhead is shown separately in the tooltip.

Each monitored qube adds one Python sampling process inside that qube plus a
persistent qvm-run process and a Rust reader thread in dom0. This overhead scales with the number of guests;
measure it on the target machine. Streams are bounded and rate-limited. At most
128 memory connections are alive or shutting down at once; any additional guests
remain unknown until capacity is available. The `--no-guest-memory` option disables
all remote RAM and swap collection (dom0 remains measured, guest allocations become red).
A `--once` snapshot intentionally starts no remote streams, so guest usage and
network rates are unknown. The running service fills those in as connections warm up.

## Validation in dom0

Automated tests and a graphical preview can run in a normal dev VM. Real Xen
measurements and dom0 packaging must still be validated on the target machine.

1. Run `sudo /usr/libexec/multiload-qubes-collector --once`. `unknown` CPU on the
   first sample is expected: CPU needs two counter samples.
2. Check service status and its file:
   `systemctl status multiload-qubes-collector` and
   `cat /run/multiload-qubes/metrics`.
3. Compare physical total/free with `sudo xl info`, and current allocations with
   `sudo xl list`. The snapshot uses KiB; `xl list` commonly displays MiB.
4. Check readings after allowing several seconds for guest connections to start.
   In a test qube, compare `MemTotal` and `MemAvailable` in `/proc/meminfo` with
   `free` and the formula above. XenStore swap keys are no longer used.
5. Touch a bounded allocation (e.g. 256 MiB) in that qube, then release it. The
   used value should respond after the next samples. Repeat with swap active;
   swap should not be added to used RAM. Pause/resume a test qube, or restart it,
   and verify that missing data is red and new readings recover automatically.
6. Exercise CPU load, start/stop qubes, ballooning, vertical orientation, panel
   restart, Properties, persisted settings, and service stop/restart. Data should
   become unavailable within a few seconds of collector failure.
7. Check idle overhead with `top`/`ps` on the collector and XFCE plugin wrapper.

Snapshot fields, units, validation and encoding/decoding live in the shared local
Rust crate `snapshot/`. Both the collector and panel depend on its `Snapshot`
type. The collector builds a typed snapshot and encodes MQ6; the panel decodes
through the same contract and applies the shared freshness policy. The shared
crate has no Xen or GTK/Cairo dependencies, so the collector keeps its existing
native dependencies. Atomic file replacement is unchanged.

The decoder accepts MQ1 through MQ6. The encoder writes MQ6 for per-domain CPU,
otherwise MQ5 for per-domain RAM, MQ4 for disk data, MQ3 for swap, or MQ2. It preserves six timestamp
decimals, four CPU decimals and three network/disk rate decimals.
Structural validation is independent of the clock. The panel additionally allows
up to five seconds of future clock skew and max(5 seconds, four collection
intervals) of age, preserving the old behavior. Workspace tests cover the shared
codec, legacy compatibility and freshness separately from rendering/collection.

The versioned snapshot format is:
`MQ1 unix_timestamp cpu_percent|unknown total_kib allocated_kib used_kib unknown_allocation_kib overhead_kib collector_period_seconds`.
MQ2 extends that format with two trailing fields: `rx_bytes_per_second tx_bytes_per_second`
(or `unknown unknown`). MQ3 appends `expected_swap_reporters swap_entries`, where
entries are comma-separated `incarnation_id:name:total_kib:used_kib` records, or
`-` if empty. IDs include the Xen domain ID and VM identity to distinguish
restarts. Names come from dom0 metadata, never guest output; the shared codec
validates bounded ASCII labels, unique names/IDs, totals and coverage. Files are
bounded to 96 KiB and 129 entries per domain metric (128 guest readers plus dom0).
MQ4 appends `read_bytes_per_second write_bytes_per_second disk_devices`. Rates
are both `unknown` while warming up or with no devices; names are comma-separated,
or `-` if none. MQ4 permits `unknown -` in the swap extension for missing swap data.
Disk names are validated ASCII, unique, at most 63 bytes each, with at most 64 disks.
MQ5 appends `expected_ram_reporters ram_entries`, with the same bounded
`incarnation_id:name:total_kib:used_kib` records as swap. RAM totals must be nonzero.
The disk device token `unknown` represents unavailable disk data in MQ5; `-`
continues to mean a known empty device list. MQ6 appends
`cpu_window_ns host_logical_cpus expected_cpu_domains cpu_entries`. CPU records
reuse `incarnation_id:name:total:used`: total is the online-vCPU time budget
(`window_ns * online_vcpus`) and used is scheduled CPU nanoseconds during that
window. MQ6 permits `unknown -` for absent per-domain RAM. The GUI continues to
accept MQ1–MQ5 snapshots during upgrades, with absent metrics shown as unavailable.

## Network collection and upgrading

Network collection requires `qvm-run` in dom0 and the existing Python 3/Qubes agent
in sys-net. No files, packages, policies or XenStore permissions are added inside
sys-net. A single persistent `qvm-run --pass-io --no-gui --no-autostart` connection
reads counters once per second. It selects device-backed interfaces in
`/sys/class/net`, excluding `lo`, `vif*` and virtual devices (including VPNs and
bridges). It counts external traffic once instead of summing each forwarding hop.
All physical NICs in the selected qube are included, even disconnected NICs.

The Rust reader runs independently of Xen collection, validates bounded numeric output,
limits incoming sample frequency, and retries after disconnection. A source that
stops reporting becomes unavailable within five seconds. Interface changes,
counter resets and source reboots establish a new baseline rather than causing
spikes. A stopped sys-net is never started by this collector. Missing network
samples appear as grey baseline marks; measured idle traffic is a real zero.

The default source is `sys-net`. To change it, use a systemd override:

```ini
[Service]
ExecStart=
ExecStart=/usr/libexec/multiload-qubes-collector --network-qube my-net-qube
```

Use `--no-network` to disable remote collection entirely; hiding the chart in
Properties only hides the chart. A `--once` snapshot has unknown network rates,
because it does not launch a persistent sampling connection.

After upgrading the RPM, run these in dom0:

```bash
sudo systemctl restart multiload-qubes-collector
xfce4-panel -r
```

The Network chart is enabled automatically for pre-0.2 settings and can be toggled
in Properties. Test a download/upload in an app qube and compare with the physical
interface counters inside sys-net. Stop/restart sys-net to check recovery. Real
qrexec traffic still needs testing on the target dom0; automated tests cover the
stream reader with local child processes, protocol validation and guest NIC selection.

## Per-qube CPU chart and upgrading

`Per-qube CPU` is enabled by default, can be hidden independently in Properties, and
appears immediately after host CPU in both panel orientations. It shares the
pixel-sharp domain graph renderer and stable per-name color tints with Qube RAM
and swap. Lines use multiload-ng's bright CPU blue `#48BDE6`, with a dark `#036F96`
maximum fill at 25% opacity. Percentages overlap instead of stacking.

The collector requests `XENSTAT_VCPU` data from libxenstat and counts only online
vCPU slots. All handles remain opaque; additional symbols are loaded through the
existing checked/owned library API. If detailed sampling fails, the collector
falls back to the original base snapshot, logs the failure once and its recovery,
and leaves per-qube CPU unavailable while keeping the other metrics running.
It requires no guest agent, sampling connection or additional guest process.

CPU percentages use the same monotonic window as host CPU. A domain's own CPU
percentage is `scheduled_ns / (elapsed_ns * online_vcpus) * 100`; its contribution
to host load uses the host logical CPU count instead. The collector excludes
internal stubdomains from per-qube lines but includes their raw time in host CPU.
At most 129 domains are graphed; the tooltip reports missing/warming-up coverage.

New/restarted domains, vCPU-count changes, resume after pause, unknown vCPU counts
and counter resets establish fresh baselines rather than false idle values or
spikes. Tiny scheduling/accounting differences are clamped to the per-domain
budget. A `--once` snapshot cannot derive per-qube CPU rates from one sample.
Xen scheduling weights, affinity and caps are not changed; the chart does not
measure runnable time denied by Xen or work performed in dom0 on a qube's behalf.

After installing v0.11.1, restart the collector and run `xfce4-panel -r`. Compare a
CPU-loaded qube with its online vCPU count in `xl list`; a four-vCPU qube at 100%
contributes 25% to a sixteen-logical-CPU host. Live Xen reporting still needs
checking in dom0; fixtures cover normalization, online counts, resets, restart,
pause/resume, serialization, chart ordering and settings.

## Per-qube RAM chart and upgrading

`Per-qube RAM` is enabled by default and can be hidden independently in Properties. It
appears immediately after host RAM in horizontal and vertical panels. Both use
existing M1/M2 guest memory frames: the collector now retains each frame's
`MemTotal` as well as used RAM. The guest payload and connection count are
unchanged. dom0 is read locally. `--no-guest-memory` leaves only dom0 reporting;
missing guest reports stay unknown instead of becoming zero usage. Paused and
internal domains are excluded, and incarnation IDs prevent lines joining across
qube restarts. The per-domain graph and tooltip code is shared with swap.

Bright lines use tints of multiload-ng's `#43D18D`; the highest-percentage fill
uses dark `#03964F` at 25% opacity. RAM and swap lines are snapped to pixel
centers and drawn without antialiasing; the fills keep their intended opacity. The chart tracks current RAM headroom within
individual domains, while the host RAM chart continues to show physical usage,
allocation and unknown usage. Guest totals are not replaced with configured
maximum memory or Xen allocation. Reclaimable memory is accounted for through
`MemAvailable`; swap is excluded.

After installing v0.11.1, restart the collector and run `xfce4-panel -r`. Compare a
qube's tooltip percentage with `(MemTotal - MemAvailable) / MemTotal * 100` from
its `/proc/meminfo`. Existing snapshots remain readable during the upgrade, but
Qube RAM needs MQ5 data from the updated collector.

## Swap collection and upgrading

The existing guest memory stream now emits
`M2 domid MemTotal MemAvailable SwapTotal SwapFree` once per second. Swap used is
`SwapTotal - SwapFree`, collected from the same `/proc/meminfo` read as RAM.
The collector also accepts old M1 reports, whose swap remains unknown. No extra
connections or guest processes are needed. dom0 uses its local `/proc/meminfo`.
Disabled swap (`SwapTotal=0`) is a valid report, distinct from a missing report.
Paused/internal domains are excluded from swap coverage; running eligible guests
without reports remain missing, including when `--no-guest-memory` is selected.

Swap capacity belongs to individual domains. Total percentage can hide one full
qube, so the graph uses each domain's own denominator. Swap occupancy does not
measure ongoing swap I/O or necessarily mean the machine is currently struggling.
Zram, if enabled, contributes its logical swap capacity/usage; this is not a
measurement of backing disk consumption or compressed physical memory.

The Swap chart is enabled automatically for older settings and can be hidden in
Properties. Upgrade the RPM, restart the collector and run `xfce4-panel -r` as
shown above. There is nothing to install inside guests. Compare the tooltip with
`SwapTotal` and `SwapFree` in `/proc/meminfo` inside a test qube; stop/restart that
qube to check gaps and new line segments. Real guest reporting still needs testing
in dom0; automated tests cover frames, accounting, coverage, histories and settings.

## Disk I/O collection and upgrading

The Rust collector reads `/sys/block/<disk>/stat`, the sysfs equivalent of the
kernel's `/proc/diskstats` counters. No guest code, extra process, package or
policy change is needed. Sector deltas are multiplied by 512 and divided by
elapsed monotonic time. This is the kernel accounting sector size, independent
of the drive's physical or logical sector size.

Device selection uses sysfs topology: whole devices with hardware backing and no
lower block devices. Partitions, virtual-device paths (including LVM, dm-crypt,
software RAID, loop and zram), optical drives, MMC boot/RPMB devices and hidden
NVMe paths are excluded. This counts the bottom device layer once instead of
adding disks, partitions and mapped guest volumes together. Hardware RAID appears
as the device(s) exposed by its controller. Unusual virtual/multipath topologies
may have no supported device rather than silently selecting another layer.

The graph covers storage attached to dom0. Disks owned by storage/USB qubes are
outside this scope. Physical counters include metadata, swap, background writeback
and other dom0 traffic; reads satisfied from caches generate no device reads.
Summed RAID member traffic can exceed application traffic because it includes
replication/parity. The chart is throughput, not latency or saturation.

The first sample, a changed device set, a detected disk replacement or a counter
reset establishes a baseline and leaves a gap. Replacement detection uses kernel
`diskseq` when available, plus device number and sysfs path. Real idle rates are
zero. Failed reads invalidate the whole disk sample, leave other charts running,
and clear the baseline; journal messages report changed failures and recovery.
`--once` lists devices but intentionally has unknown disk rates.

Disk I/O is enabled automatically for old settings and can be hidden in Properties.
After installing v0.11.1, restart the collector and panel using the commands above.
In dom0, compare the tooltip's devices and rates with `iostat -dx 1` if available,
then read/write a test file in a guest and allow for caching and delayed writes.
Automated fixtures cover device selection, rates, resets, hotplug and invalid
statistics; live host storage activity still needs checking in dom0.

## Connection diagnostics

Each guest reader has three states: waiting for usable data, reporting with a
receive timestamp, and retrying with a reason and retry deadline. Staleness is
calculated from the timestamp; stopping a reader is an internal lifecycle action.
RAM retains red unknown-allocation rendering; unavailable data is marked grey.

Diagnostics go to the collector's standard error, captured by systemd in dom0:

```bash
sudo journalctl -u multiload-qubes-collector -n 50 --no-pager
sudo journalctl -fu multiload-qubes-collector
```

Messages identify the source, for example `dev RAM` or `sys-net network`. The
first failure and any changed reason are logged. An identical failure is not
repeated on each reconnect attempt, even if the new connection warms up first.
The first usable measurement after failure logs recovery once. Normal reader
shutdown is not treated as a failure. Idle zero measurements are valid data.

Reasons cover launch/I/O failures, closed streams, timeouts and invalid reports.
Failure messages include the command's exit code or terminating signal when
available, plus a sanitized stderr excerpt. The reader retains at most 4 KiB of
stderr tail, drains excess output without keeping it, and limits each read turn to
64 KiB so stderr cannot monopolize metrics collection. Stderr does not refresh
the metrics timeout and is not streamed into the journal during normal operation.

Journal excerpts are at most 1 KiB of single-line ASCII text, plus a truncation
marker when needed. ANSI sequences are stripped using `strip-ansi-escapes`, other
controls are removed, whitespace is collapsed, and non-ASCII characters are
escaped (including bidirectional formatting characters and invalid UTF-8).

After a failure, exit-status collection waits no more than 250 ms, continuing to
drain stderr nonblockingly. A command that closes stdout but remains alive is
reported as having no exit status yet; our cleanup SIGTERM/SIGKILL is not presented
as the original cause. Status inspection uses `nix::waitid` with `WNOWAIT`, leaving
PID ownership/reaping with the existing process guard. Identical complete failure
messages are suppressed across retries; recovery is still logged once.

For example: `Guest metrics [dev RAM] unavailable: guest stream closed; command
exit status 127; stderr: python3: command not found; retrying in 3.0s`.

Out of scope: per-qube controls, a separate tray frontend, and theme import/export buttons.
